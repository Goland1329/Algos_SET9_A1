# Отчет по лабораторной работе: эмпирический анализ алгоритмов сортировки строк

В этой лабораторной работе я сравнивал обычные алгоритмы сортировки строк и их строковые версии. В тестировании участвовали:

- стандартный QuickSort;
- стандартный MergeSort;
- тернарный String QuickSort;
- String MergeSort с использованием LCP;
- MSD Radix Sort;
- гибридный MSD Radix Sort + String QuickSort.

Тесты проводились на массивах строк размером от 100 до 3000 с шагом 100. Для каждого размера рассматривались три типа входных данных: случайный массив, обратно отсортированный массив и почти отсортированный массив.

В таблицах ниже я в основном рассматриваю результаты для максимального размера `3000`, потому что на нем лучше всего видно поведение алгоритмов.

## 1. Анализ времени выполнения

### Случайный массив

На случайных данных лучшие результаты показали гибридный алгоритм **Radix + QuickSort** и стандартный **MergeSort**.

Для массива из 3000 строк получились такие времена:

| Алгоритм | Время, мс | Сравнения |
|---|---:|---:|
| Стандарт QuickSort | 19.241919 | 564493 |
| Стандарт MergeSort | 6.677918 | 75380 |
| Оптим. QuickSort | 11.280880 | 63604 |
| Оптим. MergeSort | 7.441305 | 52251 |
| Radix | 14.086832 | 0 |
| Radix + QuickSort | 6.268793 | 26108 |

На этом наборе быстрее всех оказался **Radix + QuickSort**: около `6.27 мс`. Стандартный **MergeSort** оказался почти таким же быстрым: около `6.68 мс`.

Обычный **QuickSort** работает заметно хуже, чем остальные быстрые алгоритмы. Это связано с тем, что он много раз сравнивает строки целиком и может повторно проходить по одним и тем же символам.

**Оптим. MergeSort** делает меньше сравнений, чем стандартный MergeSort (`52251` против `75380`), но по времени он чуть медленнее. Скорее всего, здесь накладные расходы на хранение и обновление LCP перекрывают выигрыш от меньшего числа сравнений.

Обычный **Radix** работает медленнее гибридной версии, потому что на нижних уровнях рекурсии он продолжает создавать корзины, даже когда подмассивы уже маленькие. Гибридный вариант в таких случаях переключается на String QuickSort, поэтому получается быстрее.

### Обратно отсортированный массив

На обратно отсортированных данных особенно хорошо видно слабое место обычного QuickSort.

Для массива из 3000 строк:

| Алгоритм | Время, мс | Сравнения |
|---|---:|---:|
| Стандарт QuickSort | 5721.022401 | 9687535 |
| Стандарт MergeSort | 21.345181 | 42671 |
| Оптим. QuickSort | 198.945695 | 169677 |
| Оптим. MergeSort | 36.931840 | 18677 |
| Radix | 59.317828 | 0 |
| Radix + QuickSort | 79.894183 | 54971 |

Самый плохой результат здесь у **стандартного QuickSort**: больше `5700 мс`. Это ожидаемо, потому что в реализации опорным элементом берем первый элемент. На обратно отсортированном массиве такой выбор приводит к сильной деградации алгоритма.

**Оптим. QuickSort** тоже замедляется, но намного меньше: около `199 мс`. То есть строковая версия лучше обычного QuickSort, но она все равно зависит от порядка входных данных.

Лучший результат по времени показал **стандартный MergeSort**: около `21.35 мс`. Он не так сильно зависит от начального порядка массива, поэтому на обратной сортировке работает стабильно.

**Оптим. MergeSort** делает меньше сравнений, чем стандартный MergeSort (`18677` против `42671`), но по времени получается медленнее (`36.93 мс` против `21.35 мс`). Значит, уменьшение числа сравнений не всегда автоматически дает выигрыш по времени.

**Radix** оказался быстрее гибридного **Radix + QuickSort** на этом наборе. Это связано с тем, что гибрид при малых подмассивах переключается на QuickSort, а на обратно отсортированных данных QuickSort работает не очень удачно.

### Почти отсортированный массив

На почти отсортированных данных обычный QuickSort снова работает хуже остальных.

Для массива из 3000 строк:

| Алгоритм | Время, мс | Сравнения |
|---|---:|---:|
| Стандарт QuickSort | 278.008309 | 1225820 |
| Стандарт MergeSort | 21.833000 | 70693 |
| Оптим. QuickSort | 60.872560 | 104504 |
| Оптим. MergeSort | 21.896701 | 29315 |
| Radix | 58.953797 | 0 |
| Radix + QuickSort | 40.483686 | 62285 |

Здесь лучше всего по времени снова выглядят **стандартный MergeSort** и **оптимизированный MergeSort**. Их времена почти одинаковые: около `21.8 мс`.

При этом **оптимизированный MergeSort** сделал намного меньше сравнений: `29315` против `70693`. То есть по числу сравнений он действительно лучше, но по времени преимущество почти не проявилось.

**Стандартный QuickSort** снова сильно проигрывает. Для 3000 строк он сделал больше `1.2 млн` сравнений и работал около `278 мс`.

Гибридный **Radix + QuickSort** оказался быстрее обычного Radix: `40.48 мс` против `58.95 мс`. На почти отсортированных данных гибридная идея с переключением на String QuickSort дала положительный эффект.

## 2. Анализ количества посимвольных сравнений

В программе считались именно посимвольные сравнения для алгоритмов, которые реально сравнивают символы между собой.

У **Radix Sort** количество сравнений равно нулю, потому что он не сравнивает символы через `<`, `==` или `>`, а использует символ как индекс корзины. Поэтому для Radix в столбце сравнений стоит `0`.

По результатам видно несколько моментов.

Во-первых, обычный **QuickSort** делает очень много сравнений на плохих входных данных. На обратно отсортированном массиве из 3000 строк он сделал `9687535` сравнений, а на почти отсортированном — `1225820`.

Во-вторых, **String MergeSort с LCP** действительно уменьшает количество сравнений. Например:

- на случайном массиве: `52251` против `75380` у стандартного MergeSort;
- на обратно отсортированном массиве: `18677` против `42671`;
- на почти отсортированном массиве: `29315` против `70693`.

То есть LCP-оптимизация работает именно по количеству сравнений. Но по времени она не всегда быстрее, потому что появляются дополнительные расходы на хранение пар `string + LCP` и обновление этих значений.

В-третьих, **Radix + QuickSort** имеет ненулевое число сравнений, потому что внутри гибридного алгоритма при малых подмассивах вызывается String QuickSort. Поэтому, например, на случайном массиве из 3000 строк у него `26108` сравнений.

## 3. Общие выводы

1. **Стандартный QuickSort** оказался самым нестабильным алгоритмом. На случайном массиве он работает приемлемо, но на обратно отсортированном массиве сильно деградирует из-за выбора первого элемента как опорного.

2. **Стандартный MergeSort** показал себя наиболее стабильным по времени. Он хорошо работает на всех трех типах массивов и не проваливается на обратном или почти отсортированном порядке.

3. **String QuickSort** лучше обычного QuickSort по числу сравнений и времени, но он тоже зависит от структуры входных данных. На обратно отсортированном массиве он заметно замедляется.

4. **String MergeSort с LCP** хорошо снижает количество посимвольных сравнений. Но по времени он не всегда лучше стандартного MergeSort, потому что сама LCP-логика добавляет накладные расходы.

5. **MSD Radix Sort** не делает посимвольных сравнений в смысле comparison sort, но имеет накладные расходы на создание корзин. Поэтому он не всегда быстрее остальных алгоритмов.

6. **Radix + QuickSort** оказался очень хорош на случайных данных: для 3000 строк он дал лучшее время `6.268793 мс`. Но на обратно отсортированном массиве гибрид оказался хуже обычного Radix, потому что переключение на QuickSort на таких данных не всегда выгодно.

Итоговый вывод: если выбирать самый стабильный алгоритм по времени, то в моих тестах лучше всего выглядит **стандартный MergeSort**. Если смотреть на случайные данные, то самым быстрым оказался **Radix + QuickSort**. А если важнее уменьшить количество сравнений строк, то хорошо работает **String MergeSort с LCP**.
